# Как изучать TaskFlow

Начни с запуска по [README](../README.md), затем выполни регистрацию и создание задачи через Swagger UI. Сохрани `accessToken` и `id` из ответов: они понадобятся для следующих запросов. Для повторения сценария есть [requests.http](../requests.http).

## С каких файлов начать

1. [TaskController.java](../src/main/java/com/taskflow/task/TaskController.java): маршруты, HTTP-статусы, DTO и параметры запроса.
2. [TaskService.java](../src/main/java/com/taskflow/task/TaskService.java): создание, изменение и поиск задач текущего пользователя.
3. [TaskRepository.java](../src/main/java/com/taskflow/task/TaskRepository.java): запросы к БД, фильтры и пагинация.
4. [Task.java](../src/main/java/com/taskflow/task/Task.java): поля сущности, связь с владельцем и серверные временные метки.
5. [AuthService.java](../src/main/java/com/taskflow/auth/AuthService.java): регистрация, проверка пароля и конфликт email.
6. [SecurityConfig.java](../src/main/java/com/taskflow/config/SecurityConfig.java): открытые маршруты и проверка Bearer-аутентификации.
7. [TaskServiceTest.java](../src/test/java/com/taskflow/task/TaskServiceTest.java): небольшие примеры проверки поведения сервиса.

## Как проходит запрос

Рассмотрим `POST /api/tasks`:

1. Spring Security проверяет Bearer token до вызова контроллера.
2. `TaskController` получает проверенный `Jwt` и `CreateTaskRequest`. Bean Validation проверяет обязательный непустой `title` и ограничения длины.
3. Контроллер берёт ID владельца из `sub` токена. Клиент не задаёт владельца в JSON.
4. `TaskService` подставляет `TODO` и `MEDIUM`, если соответствующие значения отсутствуют или равны `null`, и создаёт `Task`.
5. `TaskRepository` сохраняет сущность через JPA в PostgreSQL. `@PrePersist` устанавливает обе временные метки.
6. Сервис вручную собирает `TaskResponse`. Контроллер возвращает `201` с телом и заголовком `Location`.

У `Task` одна связь `ManyToOne` с пользователем; обратная коллекция задач в `User` не нужна. DTO задают явный контракт API и не позволяют случайно вернуть `passwordHash` или внутреннюю JPA-связь.

`PUT` полностью заменяет редактируемые поля: `title`, `status`, `priority` обязательны; пропущенные или равные `null` поля `description` и `dueDate` очищаются. Прошлая `dueDate` допустима. `id`, владелец и дата создания не редактируются. Перед сборкой ответа сервис выполняет `saveAndFlush`, чтобы получить временную метку, обновлённую обработчиком `@PreUpdate`.

## Вход и проверка JWT

`RegisterRequest` и `LoginRequest` нормализуют email: убирают пробелы по краям и приводят его к нижнему регистру. При регистрации `PasswordEncoder` сохраняет BCrypt-хеш. Открытый пароль не записывается в БД. Вход сравнивает пароль с хешем через `matches`, а не повторным сравнением двух хешей: BCrypt использует соль.

Сервис сначала проверяет наличие email, но окончательную уникальность гарантирует ограничение `uk_users_email` в PostgreSQL. Оно закрывает ситуацию, когда две одновременные регистрации успели пройти предварительную проверку.

[JwtService](../src/main/java/com/taskflow/auth/JwtService.java) выдаёт токен с ID пользователя в `sub`, издателем `taskflow`, временем выдачи и сроком действия. По умолчанию срок — один час. [JwtConfig](../src/main/java/com/taskflow/config/JwtConfig.java) использует стандартный Nimbus encoder/decoder, HS256 и Base64-секрет из окружения с минимум 32 декодированными байтами.

При каждом защищённом запросе Spring Security проверяет подпись, срок действия, издателя и корректность ID в `sub`. Повреждённый или просроченный токен даёт `401`. JWT подписан, но не зашифрован, поэтому в него нельзя помещать пароли и другие секреты. Здесь в токене нет пароля или email.

Сессии, cookie-аутентификация, HTTP Basic и форма входа не используются. CSRF отключён для этого API, потому что учётные данные передаются явно в заголовке `Authorization`, а не прикрепляются браузером автоматически. Если позже появится cookie-аутентификация, эту настройку придётся пересмотреть. Refresh token и серверный отзыв отдельных токенов в этой версии не реализованы.

## Почему чужую задачу нельзя получить

Чтение, изменение и удаление используют `findByIdAndOwnerId(id, ownerId)`. Проверка входит в запрос к БД. Если задача принадлежит другому пользователю или не существует, результат одинаковый: `404` с сообщением `Task not found`. Изменение начинается только после успешного поиска.

Список также фильтруется по `owner.id` в репозитории. Поэтому ограничение действует и на `items`, и на `totalElements`, а не только на показанные строки. Сортировка по `createdAt DESC, id DESC` сохраняет однозначный порядок, даже если время создания совпало.

## Unit- и интеграционные тесты

`./mvnw test` запускает unit-тесты без Docker. В `TaskServiceTest` репозиторий заменён Mockito-моком: мы проверяем значения по умолчанию, очистку необязательных полей, передачу владельца и отсутствие записи после неуспешного поиска. Такие тесты быстрые, но не доказывают корректность SQL или настроек Spring Security.

`./mvnw verify` дополнительно запускает классы `*IT` через Maven Failsafe. [TaskFlowApiIT](../src/test/java/com/taskflow/TaskFlowApiIT.java) поднимает Spring-приложение и настоящий PostgreSQL через Testcontainers. Запросы проходят через MockMvc, реальные фильтры безопасности, сервисы и репозитории; JWT получается через API регистрации или входа. Тесты проверяют HTTP-ответы и состояние БД, включая сохранность чужой задачи после запрещённого изменения и удаления.

Данные очищаются перед каждым интеграционным тестом. Нет зависимости от порядка тестов, заранее известного ID или `Thread.sleep`. Для проверки просроченного JWT создаётся токен с прошлым сроком действия, поэтому ждать истечения часа не нужно. Если Docker недоступен, интеграционные тесты должны завершиться ошибкой, а не молча пропуститься. JaCoCo помогает находить непроверенные ветки, но процент покрытия не заменяет проверку полезных сценариев.

## Как добавить одно поле в Task

Пример для самостоятельной практики — необязательное `estimatedMinutes`:

1. Определи правила: допустимы ли `0` и отрицательные значения, что означает `null`, очищает ли отсутствие поля значение при `PUT`.
2. Создай новую миграцию `V3__add_estimated_minutes.sql`. Уже применённые миграции не редактируй.
3. Добавь поле в `Task`, соответствующие DTO и ручное преобразование в `TaskResponse`.
4. Передай значение через `TaskService` и добавь Bean Validation к DTO.
5. Допиши unit-тест бизнес-правил и интеграционные тесты сохранения, чтения и невалидного значения. Проверь, что изоляция владельцев сохранилась.
6. Обнови примеры запросов и документацию; выполни `./mvnw verify`.

Это инструкция для будущего изменения: поля `estimatedMinutes` сейчас в проекте нет.

## Вопросы для собеседования

- Почему контроллер не обращается к репозиторию напрямую?
- Чем DTO отличается от JPA Entity? Чем опасно возвращать Entity из API?
- Почему проверки email в Java недостаточно без уникального ограничения в БД?
- Чем аутентификация отличается от проверки владельца задачи?
- Почему для чужого и отсутствующего ID возвращается одинаковый `404`?
- Для чего нужны `@Transactional`, `saveAndFlush` и второй ключ сортировки `id`?
- Что unit-тест с Mockito не проверит, а тест с PostgreSQL обнаружит?
- Каковы ограничения JWT без механизма отзыва и refresh token?

## Три небольших задания

1. Добавь необязательное поле `estimatedMinutes` по шагам выше и протестируй его границы.
2. Добавь необязательный фильтр `dueBefore` к списку задач. Заранее реши, включать ли указанную дату и задачи без срока; сохрани фильтрацию по владельцу и корректные счётчики.
3. Напиши отдельный интеграционный тест, который при одинаковом `createdAt` проверяет порядок `id DESC` для отфильтрованного списка на двух страницах.

Эти задания не реализованы заранее. Начни с одного, сделай небольшой осмысленный коммит и объясни себе, какое поведение проверяет каждый новый тест.
